# Comparisons and Benchmarks

This page is the "show your work" companion to the homepage copy.

`react-mnemonic` is intentionally more explicit than lighter persistence hooks,
but that explicitness has real tradeoffs. The goal here is not to "win" every
category. The goal is to publish fair, reproducible receipts so people can
choose the right tool for their app.

## AI friendliness benchmark

For `react-mnemonic`, the most important benchmark is not bundle size. It is:

- can an AI choose persistence without being told to reach for raw
  `localStorage`?
- can it persist the right state and leave ephemeral UI state alone?
- can it select SSR, nullable, and migration semantics correctly without extra
  user steering?

To measure that, the repo now includes an AI-friendliness benchmark under
`benchmarks/ai-friendliness/`. It is now structured as a fixed-model,
multi-library protocol:

- the same seven UI-building scenarios for every library
- the same initial user prompts, without storage implementation hints
- automated semantic scoring plus a short human review rubric
- model metadata captured in every run manifest so results stay reproducible

The benchmark assumes the agent-facing surfaces from issues #29 and #30 are
available: canonical `docs/ai/` content, instruction packs, `llms.txt`
exports, and prompt guardrails.

### Benchmark protocol

- Comparison axis: `libraries, fixed model`
- Scoring mode: `hybrid`
- Scenarios: `{aiReport.scenarios.length}`
- One-shot threshold: automated `>= 85`, human `>= 75`, zero follow-ups, and no critical failures
- Human rubric dimensions: persistence appropriateness, semantic nuance correctness, and unnecessary user intervention

The machine-readable report records:

- model provider, model ID, run date, and prompt-pack version
- per-scenario transcript and submission paths
- follow-up prompt count plus first-attempt compile/test status
- automated semantic score, human review score, semantic score, and intervention-adjusted score

### Why this matters more than bundle size

- A smaller persistence hook is not automatically easier for an agent to use
  correctly in a real app-building task.
- `react-mnemonic` is intentionally optimizing for the path where a user says
  "build the UI" and the agent still chooses durable state, SSR options, and
  migration hooks correctly.
- The benchmark protocol is stable before public cross-library results are
  published, so new runs extend the same scoreboard instead of changing the
  rules after the fact.

### Notes on the numbers

- `use-local-storage-state` and `zustand/persist` are the lightest options in
  this common-task bundle comparison.
- `react-mnemonic/core` is the minimal persisted-state entrypoint. Import
  `react-mnemonic/schema` or the root `react-mnemonic` entrypoint when you
  want schema validation, autoschema, and migrations.
- `react-mnemonic` is not aiming to be the smallest persisted-value hook. Its
  optional schema-aware footprint buys explicit schemas, recovery flows,
  namespace isolation, and more first-class SSR controls.
- `jotai/atomWithStorage` sits in the middle here because you get the atom
  model plus storage utilities, not just a single-purpose localStorage hook.

## SSR and Hydration Behavior

This section is qualitative. It focuses on what each library makes explicit for
the "persist browser storage in a server-rendered app" problem.

| Library                       | Default server render contract                     | Explicit server placeholder control      | Explicit "delay storage read until after mount" control | Notes                                                    |
| ----------------------------- | -------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| `react-mnemonic`              | Server render uses `defaultValue`                  | `ssr.serverValue`                        | `ssr.hydration: "client-only"`                          | Strongest built-in SSR contract in this comparison       |
| `use-local-storage-state`     | Server render uses `defaultValue`                  | `defaultServerValue`                     | Not a separate first-class mode                         | Strong SSR-oriented hook API for direct localStorage use |
| `usehooks-ts/useLocalStorage` | Server render starts from the initial value        | No separate server placeholder value     | `initializeWithValue: false`                            | Good for lighter SSR-safe localStorage usage             |
| `zustand/persist`             | Store initializes first, then persistence hydrates | Manual                                   | `skipHydration` plus `rehydrate()`                      | Flexible, but more store-level wiring                    |
| `jotai/atomWithStorage`       | Atom starts from `initialValue`                    | No dedicated per-atom server placeholder | Manual client-only rendering pattern                    | Works, but SSR mismatch handling is more app-managed     |

## API ergonomics for the same task

The common "persist a theme" task looks like this conceptually:

| Library                       | Shape of the persisted theme example                   | Built-in version/migrate support | Built-in recovery helpers         | Built-in namespace boundary |
| ----------------------------- | ------------------------------------------------------ | -------------------------------- | --------------------------------- | --------------------------- |
| `react-mnemonic`              | Provider + `useMnemonicKey("theme", { defaultValue })` | Yes                              | Yes                               | Yes                         |
| `zustand/persist`             | Store factory + `persist(...)` middleware              | Yes                              | Manual                            | Manual                      |
| `jotai/atomWithStorage`       | `atomWithStorage(...)` + `useAtom(...)`                | No first-class versioning        | Manual                            | Manual                      |
| `use-local-storage-state`     | Single hook call                                       | No                               | Partial (`removeItem`)            | Manual                      |
| `usehooks-ts/useLocalStorage` | Single hook call                                       | No                               | Partial (returns remove callback) | Manual                      |

### Where react-mnemonic is intentionally more explicit

- Namespace boundaries are provider-scoped instead of relying on every hook
  callsite to keep string keys coordinated manually.
- SSR behavior is part of the hook contract instead of being left to generic
  storage timing workarounds.
- Recovery flows, versioned envelopes, and read-time reconciliation are
  designed as first-class persistence concerns, not add-on conventions.

### Where alternatives are stronger today

- If you want the smallest direct localStorage hook for a simple value,
  `use-local-storage-state` and `usehooks-ts` have a lower footprint.
- If your team already uses Zustand broadly, `persist` benefits from the wider
  ecosystem and store middleware story.
- If your app is already modeled around atoms, `jotai/atomWithStorage` keeps
  persistence aligned with that mental model.

## Bottom line

Choose `react-mnemonic` when you want persistence to be a named, explicit part
of your architecture: schemas, migrations, recovery UX, namespace isolation,
and deterministic SSR behavior.

Choose a lighter hook or store utility when the problem is narrower: "keep this
single client value in localStorage" and move on.
